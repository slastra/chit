# chit design

This is the contract between the server, `chitd`, and the app. Change it here first, then
in code.

## Pieces

| Piece | What it is |
|---|---|
| `chit-server` | PocketBase embedded as a library, plus the sync routes below |
| `chitd` | Desk daemon: SQLite replica, unix socket, SSE client, reminder timers |
| `chit` | CLI that talks to `chitd` |
| `app/` | The Flutter app (Linux, Android, web): its own SQLite replica and sync engine, a port of `chitd`'s |

PocketBase owns accounts, the admin UI, file storage and backups. Clients do **not** use
PocketBase's record CRUD or its realtime API for notes. PocketBase realtime has no replay,
so a client that was offline would miss changes. Everything note-shaped moves through the
op log.

## Data model

Collections are defined in `migrations/`.

| Collection | Shared or per user | Fields |
|---|---|---|
| `notes` | shared | owner, kind (`text`, `list`), title, body, color, trashed, deleted |
| `items` | shared | note, text, checked, order, indent (0 or 1), deleted |
| `note_members` | shared | note, user, role (`editor`, `viewer`) |
| `note_state` | per user | note, user, pinned, archived, labels, reminder, reminder_done |
| `labels` | per user | user, name, deleted |

This split matches Keep. Collaborators share the content and color. Each person pins,
archives, labels and sets reminders on their own.

Records are never hard-deleted by sync. `deleted` is a tombstone so the deletion itself can
replicate. Compaction purges old tombstones later.

Record ids are generated by clients, so a note made offline already has its final id. They
use PocketBase's format: 15 characters from `[a-z0-9]`.

## Clocks and merging

Every synced record carries `clocks`, a JSON object mapping field name to the hybrid
logical clock (HLC) of that field's last write:

```json
{"text": "1795692999119-0003-k3j9x2", "checked": "1795692999412-0000-p0a7m1"}
```

An HLC string is `<unix ms, 13 digits>-<counter, 4 hex digits>-<device id>`, so plain
string comparison orders them. A write to a field applies only if its HLC is greater than
the stored one. Otherwise it is dropped, and the sender learns the winning value from the
feed.

Each checklist item is its own record, so concurrent check-offs never collide. Order uses
fractional index keys (`order`), so moving an item rewrites one field. Two offline edits
to the same note body resolve to the later write.

## Sync routes

All routes need a user token (`Authorization: <token>` from PocketBase auth) and live under
`/api/chit`. Clients name their device with the `X-Chit-Device` header (or `?device=`), 1 to
16 characters of `a-z0-9`. Wire types are in `internal/protocol`.

### `POST /ops`

The body is a batch of ops, at most 1000:

```json
{"device": "k3j9x2", "ops": [
  {"collection": "items", "id": "…", "field": "checked", "value": true, "hlc": "…"}
]}
```

Writable collections and fields:

| Collection | Fields | Who |
|---|---|---|
| `notes` | kind, title, body, color | owner, editors |
| `notes` | trashed, deleted | owner |
| `items` | note (on create only), text, checked, order, indent, deleted | owner, editors |
| `labels` | name, deleted | the label's user |
| `note_state` | pinned, archived, labels, reminder, reminder_done | anyone who can see the note, for themselves |

The first op on an unknown id creates the record, so a new note's ops carry `kind`, and a
new item's ops carry `note`. Ops for `note_state` use the **note's id** as `id`: each user has
one state row per note, and the server finds it.

The whole batch runs in one transaction, but ops are judged one record at a time. Each op
gets a result, in request order:

```json
{"seq": 41, "results": [{"applied": true}, {"stale": true}, {"error": "only the owner can set trashed"}]}
```

`stale` means a newer write already holds the field, which is normal after offline edits.
`error` means the op will never apply (bad field, bad value, no permission, an HLC more than
10 minutes ahead of the server); the client drops it rather than retrying.

A client already applied the op to its own replica, so a refused one must be undone
there: it reloads the snapshot. It ends its stream first and opens a new one from the
snapshot's `seq`. A snapshot loaded under an open stream loses any change the stream
delivered after the snapshot was taken, because the stream has already moved past it.

- Within a batch, `notes` and `labels` records are applied before the rest, so a batch
  may name a new note's items or state ahead of the note.
- Date fields (`trashed`, `reminder`) take RFC 3339 in UTC, or `""` to clear. Anything
  else is an `error`.

### `GET /snapshot`

Everything the caller can see as of `seq`: notes, items, members, the caller's state rows
and labels. Deleted records are left out. Stateless clients (the CLI) read from this; a
replica uses it for the first sync and after `reset`.

### `GET /changes?since=N`

The changes after `N` visible to the caller, at most 500, plus the next cursor and `more`.
Visibility is checked against current membership. The caller's own device's changes are
left out. A change is one of:

| `kind` | Meaning |
|---|---|
| `set` | One field changed: `field`, `value`, `hlc` |
| `record` | A whole record in `value`: sent on create, and to a new member for the shared note, its items and its members |
| `remove` | A membership ended (`record` is the membership id) |
| `revoke` | The reader lost access to note `record`; drop it locally |

### `GET /stream` (SSE)

The same feed, live. The cursor comes from `Last-Event-ID` on a reconnect, or `?since=`.

```
id: 1234
event: change
data: {"seq":1234,"kind":"set","collection":"items","record":"…","field":"checked","value":true,"hlc":"…","by":"…"}

id: 1240
event: cursor
data: {}

: ping
```

- `cursor` moves the client's `Last-Event-ID` past rows it cannot see, so a reconnect does
  not rescan them.
- `: ping` every 50 s. A client that hears nothing for two pings treats the stream as dead
  and reconnects.
- After each write the server wakes every open stream, and each re-reads the feed from its
  own cursor, so the stream and `/changes` share one visibility check.
- Leaving out the device header gets every change, the caller's own included. `chit watch`
  does this.
- Planned: a `reset` event once old changes are compacted.

### Text merges

`title` and `body` on notes and `text` on items are free text. An op on one may carry
`base`: the clock of the value the edit started from. If the field's clock is no longer
`base` (someone wrote it meanwhile), the server does not keep the later of the two. It
finds the base value in the log and joins the edits word by word (`internal/merge`):

- a stretch only one side changed takes that change;
- a stretch both changed differently keeps both, what was there first, then the edit.

The result is stamped with a server clock past both edits and goes out on the feed to
everyone, the sender's device included (it holds only its half). The op's result says
`"merged": true`. Without `base` (the CLI, chitd) the later write wins as before.

The app runs the same merge (`app/lib/core/merge.dart`, the same cases in
`internal/merge/testdata`) when someone's edit arrives while a field is being typed in,
keeping the cursor in place, then sends the result with the new base.

### Presence

Who has a note open is kept in memory only, never in the log.

- `POST /presence` with `{"note": "…", "editing": bool, "gone": bool}`: anyone who can
  see the note. A device with a shared note open says so every 15 seconds and when it
  starts typing; `gone` when it leaves. The server forgets a device 40 seconds after its
  last word and stops showing it as typing 8 seconds after its last keystroke.
- The stream sends `event: presence` with `{"note", "user", "device", "editing", "gone"}`
  to everyone who can see the note, except the device it is about. It has no `id`, so
  it moves no cursor; a new stream gets everyone present first. Clients that do not
  know the event ignore it.

### Sharing

- `POST /notes/{id}/members` with `{"user": "…", "role": "editor" | "viewer"}`: owner only.
  Adds the member or changes their role. A new member's feed gets the note, its items and
  its members as `record` changes first.
- `DELETE /notes/{id}/members/{user}`: the owner removes anyone, or a member removes
  themselves. The member's own state row for the note is deleted, and they get `revoke`.

Any signed-in user can list the accounts on the instance
(`GET /api/collections/users/records`), to pick who to share with.

## Attachments

Files on a note live in the `attachments` collection (note, file, name, size, type,
deleted), stored by PocketBase on disk under `/pb_data/storage` (or S3/R2 if configured in
the admin UI). The limit is 250 MB per file (`protocol.MaxAttachmentSize`); the upload route
carries its own body limit to match, past PocketBase's default 32 MB.

- **Upload:** `POST /api/chit/notes/{id}/attachments`, multipart with `file` and `id` (a
  client-generated record id). Owner and editors only. Retrying with the same `id` returns
  the attachment that already landed instead of storing a second copy. The server records
  the original filename, the size, and a content type sniffed from the bytes (falling back
  to the extension). Feed: a `record` change on the note.
- **Download:** the file is protected. Get a short-lived token with `POST /api/files/token`,
  then `GET /api/files/attachments/{id}/{file}?token=…`. Anyone who can see the note can
  download; everyone else gets 404. Add `&thumb=320x320` or `&thumb=1080x0` for an image
  preview.
- **Remove:** an op setting `deleted` on the attachment (owner and editors). Nothing else
  on an attachment is writable through ops, and ops cannot create one.
- A new member's share snapshot includes the note's attachments.

## Notifications

There is no push service: no FCM, no ntfy.

- **Reminders** are scheduled on each device from its replica: exact alarms on the phone,
  timers in `chitd` that become lastshell toasts. Marking a reminder done syncs
  `reminder_done`, and every device cancels its alarm or notification.
- **Shared-note activity** reaches a phone through a WorkManager catch-up every 15 minutes
  while the app is closed (sooner with the battery optimization exemption the app offers),
  and through the open stream while it runs. A Wear app is not built; the watch shows the
  phone's notifications.

## Later: suggested labels

Not built yet. Agreed design, 2026-11-26:

- **The server decides**, so the key stays off devices and every client gets it: chit-server
  holds the OpenRouter key and answers per person (labels are personal state).
- **Jev first** (`typesafe/jev-1.13`, OpenRouter Decisions API): one `noul` question per
  existing label, all in one call. The state carries the note (title, text, open items) and,
  for each label, a few titles of notes already under it, so a bare name like "Home" has
  meaning. Code, not Jev, filters and trims the state.
- **Bands:** high confidence applies the label with an Undo (only once tuned; at first
  everything is a suggestion); middling is offered; nothing fits goes to a cheap generative
  model (Claude Haiku 5.5 or Gemini Flash-Lite) for a new name, given the existing labels so it
  doesn't coin "Shopping" beside "Groceries". Code folds near-duplicates (case, plurals) into an
  existing label.
- **Not a dialog:** when a new note closes, a suggestion appears ("Label as Recipes? ✓ /
  Other…"); Other opens the full picker with the model's alternatives and existing labels.
- **When it runs:** only for notes with no label, enough text, not just a picture, and no
  suggestion already dismissed. Never while typing.
- **Privacy:** note text goes to OpenRouter and the model's provider, so each person can turn
  suggestions off.
- **Tuning:** log every suggestion with the person's accept or reject; set the auto-apply
  threshold from those choices, then pin the Jev version.
